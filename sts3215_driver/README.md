# Драйвер двух ведущих колёс

Рабочий executable — `diff_drive_node`, исходники — `src/diff_drive_node.cpp`
и `include/diff_drive_node.hpp`. Прежние `src/node.cpp` / `include/node.hpp`
сохранены как терминальный прототип одного мотора и больше не входят в сборку.

## Геометрия и направления

| Параметр | Значение |
|---|---|
| Левый / правый ID | 1 / 2 |
| Диаметр ведущей шины | 0.075 м |
| Колея по центрам | (0.200 + 0.250) / 2 = 0.225 м |
| Ширина каждой шины, при одинаковых колёсах | (0.250 − 0.200) / 2 = 0.025 м |
| Расстояние между передней и задней осью | 0.140 м, для описания шасси |

Параметры находятся в `config/params.yaml` и задаются до запуска.
`left_wheel_direction=-1`, `right_wheel_direction=1` учитывают наблюдение оператора:
при исходных знаках `+1/-1` оба колеса вращались назад. Знаки инвертированы,
повторная физическая проверка ещё не выполнена;
положительная скорость каждого колеса должна двигать соответствующую сторону вперёд.
Те же знаки применяются к показаниям энкодеров. Проверять отдельно с вывешенными колёсами.

Кинематика: `v_left = v − omega × 0.225 / 2`,
`v_right = v + omega × 0.225 / 2`. Скорости регистров трактуются как тики/с,
4096 тиков на оборот. При достижении ограничения пара масштабируется совместно,
сохраняя отношение скоростей. Ограничены скорость базы (не более 0.25 м/с),
скорости обоих колёс (не более 0.25 м/с и 3400 тиков/с), угловая скорость и разгон.
С шиной 75 мм предел 3400 тиков/с соответствует примерно 0.196 м/с на колесе.
Фактическую скорость и эффективный диаметр необходимо откалибровать на роботе.

## Сборка и mock

```bash
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install --packages-select sts3215_driver
source install/setup.bash
export ROS_DOMAIN_ID=42
ros2 launch sts3215_driver driver.launch.py
```

В другом терминале с тем же окружением:

```bash
ros2 topic pub --rate 20 /cmd_vel geometry_msgs/msg/Twist '{linear: {x: 0.05}, angular: {z: 0.0}}'
ros2 topic echo /odom
```

Mock не открывает UART. Одометрия моделируется по приложенным скоростям колёс.
Прекращение публикации команды запускает watchdog.
Диагностика публикуется в `/diagnostics`, время и watchdog используют монотонные часы;
mock работает в реальном времени, а не по `/clock` симулятора.

## Подключение приводов

После проверки ID и направлений на вывешенных колёсах:

```bash
ros2 launch sts3215_driver driver.launch.py mock_hardware:=false serial_port:=/dev/ttyUSB0
```

Для другого адаптера можно задать `serial_port:=/dev/ttyACM0`.
Скорость — 1 Мбод, 8N1. Требуются ответы на WRITE (регистр Response Status Level = 1)
и поддержка Sync Read прошивкой обоих приводов. Настройка wheel mode проверяется чтением:
если режим не применился, привод остаётся в состоянии ошибки; следует проверить блокировку EPROM.
Нода не меняет ID, скорость порта или уровень ответов сервоприводов.

При запуске отправляется нулевая скорость, для каждого мотора отключается момент,
обнуляется заданная скорость, включается wheel mode, проверяется режим и включается момент.
Внутренняя рампа ускорения сервопривода обнуляется: плавность задаёт нода.
Ответы проверяются по ID, длине, checksum и битам ошибок. Позиция, скорость,
напряжение и температура считываются одним Sync Read; телеметрия выводится в `/diagnostics`.
Ограничение ожидания UART — 8 мс по умолчанию (один deadline на оба ответа).
При USB-задержках выше этого порога будет зафиксирована ошибка; настройку адаптера
и устойчивость частоты 50 Гц нужно проверить на Raspberry Pi.

## Остановка и ошибки

- По истечении 200 мс без `/cmd_vel` начинается торможение с `watchdog_deceleration=1.0 м/с²`.
  При 0.196 м/с оно занимает ещё около 196 мс плюс дискретность цикла 20 мс и задержки I/O.
  Это не обещание полной физической остановки за 200 мс; тормозной путь проверяется отдельно.
- При новой корректной команде после обычного watchdog управление возобновляется.
- Ошибка UART, скачок энкодера, NaN/Inf в команде или пауза цикла более 100 мс
  фиксируют неисправность до перезапуска. Нода пытается отправить нулевые скорости
  и отключить момент обоих моторов, затем повторяет нулевые команды.
- При неисправности `/odom` и соответствующий TF перестают публиковаться:
  неизвестное перемещение не заменяется фиктивной неподвижностью.
- При штатном завершении, включая SIGINT, предпринимаются остановка и отключение момента.
  При физическом обрыве UART, SIGKILL, зависании ОС или потере питания Pi доставка
  команды остановки невозможна. Независимый аппаратный watchdog пока не реализован.

## Одометрия, TF и проверки

`/cmd_vel` принимает `geometry_msgs/msg/Twist` (используются `linear.x` и `angular.z`).
Очередь — одна команда. `/odom` и `odom -> base_footprint` публикуются на частоте 50 Гц.
На оборудовании одометрия считается по приращениям энкодеров с обработкой перехода через ноль.
Ковариации заданы начальными оценками и требуют полевой калибровки.

Остальное TF-дерево ещё не реализовано: `base_footprint -> base_link -> camera_link`
будет публиковать `ijkbot_description`, `map -> odom` — подсистема локализации.
Драйвер не публикует фиктивный `map -> odom`.

```bash
colcon test --packages-select sts3215_driver
colcon test-result --verbose
```

Тесты проверяют прямой ход, поворот, дугу, ограничения скоростей, торможение,
переход энкодера через ноль; обмен пакетами и неисправные ответы через PTY;
реальные ROS-топики в mock, watchdog, согласованность одометрии/TF,
блокировку после некорректной команды и валидацию параметров.
Тесты ROS изолированы доменом 177 и localhost; физические приводы не используются.

Формат обмена сверялся с [документацией протокола Waveshare](https://files.waveshare.com/upload/2/27/Communication_Protocol_User_Manual-EN%28191218-0923%29.pdf),
регистры и знаковое представление — с [реализацией Feetech SMS_STS](https://gitee.com/ftservo/FTServo_Linux/blob/main/src/SMS_STS.cpp)
и [таблицей адресов библиотеки](https://gitee.com/ftservo/FTServo_Linux/blob/main/src/SMS_STS.h).
